# JS MCQ API

Express and MongoDB API serving the learner client (`client/`) and the admin app (`admin/`).

## Structure

```text
backend/
  src/
    config/            Environment validation and MongoDB connection lifecycle
    models/             Mongoose schemas and indexes
    routes/             HTTP routes, request validation, and response shaping
    services/           Authentication and content/business operations
    utils/              Shared auth middleware, validation schemas, and errors
    app.js              Express middleware and route registration
    server.js           Database-first startup and graceful shutdown
```

Request flow is `route -> validation -> service -> model/database -> route response`; shared middleware and errors live in `utils/`.

## Requirements

- Node.js 20.19+ or 22.12+
- MongoDB 6+

## Setup

From the repository root, create the backend environment file:

```powershell
Copy-Item backend\.env.example backend\.env
```

Set `MONGODB_URI` to the connection URI for the MongoDB instance you want to use and set `JWT_SECRET` to a cryptographically random value of at least 32 characters in `backend\.env`. The two origin variables must match the client and admin web origins exactly. The API loads this file directly from `backend\.env`, validates required settings at startup, and waits for `mongoose.connect()` to succeed before listening for requests. It will not start with a missing or invalid MongoDB URI.

Install the API dependencies and start the backend:

```powershell
npm install --prefix backend
npm run dev --prefix backend
```

The health endpoint is `GET http://localhost:3000/api/health`.

## Administrator accounts

Anyone can request an account with `POST /api/auth/register` (the admin app's **Request access** screen). New accounts are always created with `isActive: false` and cannot sign in until an active administrator approves them on the **Administrators** page.

- Registration returns the same response whether or not the email is already registered, so it can't be used to discover accounts.
- Signing in to an unapproved account with the correct password returns `403` with a "waiting for approval" message; a wrong password always returns `401`.
- Deactivating an account takes effect on its next request, because every admin request re-checks `isActive`.
- Administrators can't deactivate or delete their own account, so there is always at least one active administrator.

**First administrator:** on an empty database nobody can approve the first registration. Register through the admin app, then activate that account once in MongoDB:

```js
db.admins.updateOne({ email: "you@example.com" }, { $set: { isActive: true } })
```

Passwords must be 12–200 characters. Admin login issues a short-lived JWT in an HttpOnly, SameSite=Strict cookie; production also requires HTTPS.

## Content model

Content is organised as **technology › section › topic › question**:

- `technologies` — top-level entries in the learner sidebar (JavaScript, React, System Design). Fields: `name`, `slug`, `order`, `isActive`.
- `sections` — groups inside a technology (Output Based, Concepts). Fields: `technologyId`, `name`, `slug`, `membershipUrl`, `order`, `isActive`. `membershipUrl` is where the learner app's "Buy Membership" button points for every locked item in the section.
- `topics` — subjects inside a section (Closures, Promises). Fields: `technologyId`, `sectionId`, `name`, `slug`, `mediumUrl`, `isPaid`, `order`, `isActive`.
- `questions` — `technologyId`, `sectionId`, `topicId`, `displayOrder`, `title`, `label`, `content`, `answer`, `mediumUrl`, `compilerUrl`, `isPaid`. Clients send only `topicId`; the API copies the technology and section from that topic.

Rules the API enforces:

- **Slugs are generated by the API** from the name and are never accepted from clients. They are unique among siblings (a `-2`, `-3`… suffix is added when needed), so the same topic name can exist in several sections. Renaming a record regenerates its slug, which changes its learner URL.
- **Names are unique among siblings**, compared case-insensitively, and must contain at least one letter or number.
- **Ordering:** lists are sorted by `order`, then name. `order` is optional on create; new records are appended. Topics and questions can be reordered in bulk.
- **Visibility:** records with `isActive: false`, and everything under them, are hidden from the public API but still visible to admins.
- **Deletion** is blocked while a record still has children.

### Premium content

`isPaid` locks content server-side, so locked data never reaches the learner app:

- A paid **topic** has its `mediumUrl` blanked in the public catalog, and its questions endpoint returns `[]`.
- A paid **question** is listed with its title and prompt content, but `answer`, `mediumUrl` and `compilerUrl` are returned empty.
- The public catalog marks each topic with `isPaid` and `hasPaidQuestions` so the learner app can show locked states and the membership banner.

## API

### Public

- `GET /api/public/technologies` — active technologies › sections › topics, with `questionCount` on each section and topic.
- `GET /api/public/technologies/:technologySlug/sections/:sectionSlug/topics/:topicSlug/questions` — a topic's questions in display order. Answers of free questions are included so the learner UI can reveal them on demand; this is not an answer-submission or grading API.

### Admin authentication

- `POST /api/auth/register` — body `{ "name": "...", "email": "...", "password": "..." }`. Creates an inactive account and returns `202`. Limited to 5 attempts per hour.
- `POST /api/auth/login` — body `{ "email": "...", "password": "..." }`. Limited to 10 attempts per 15 minutes.
- `GET /api/auth/me` — current authenticated administrator.
- `POST /api/auth/logout` — clears the session cookie.

Send credentials with browser requests (`credentials: 'include'`). The API only permits origins configured by `CLIENT_ORIGIN` and `ADMIN_ORIGIN`; state-changing browser requests with a different origin are rejected.

### Authenticated authoring

All paths below require the admin session cookie:

- `GET /api/admin/admins` — every administrator with `name`, `email`, `isActive` and `createdAt`.
- `PATCH /api/admin/admins/:id` — body `{ "isActive": true | false }`; approve, reactivate or deactivate an account (not your own).
- `DELETE /api/admin/admins/:id` — reject a pending request or remove an account (not your own).
- `GET /api/admin/catalog` — the full tree including hidden records, with `questionCount` per topic.
- `POST /api/admin/technologies`; `PATCH`, `DELETE /api/admin/technologies/:id`. Body: `name`, optional `order`, `isActive`.
- `POST /api/admin/technologies/:technologyId/sections`; `PATCH`, `DELETE /api/admin/sections/:id`. Body adds optional `membershipUrl`.
- `POST /api/admin/sections/:sectionId/topics`; `PATCH`, `DELETE /api/admin/topics/:id`. Body adds optional `mediumUrl`, `isPaid`.
- `PATCH /api/admin/topics/reorder` — body `{ "sectionId": "<id>", "topicIds": ["<id>", "..."] }`; reorder every topic in a section.
- `GET /api/admin/questions` (optional `technologyId`, `sectionId`, `topicId` filters), `POST /api/admin/questions`; `PATCH`, `DELETE /api/admin/questions/:id`.
- `PATCH /api/admin/questions/reorder` — body `{ "topicId": "<id>", "questionIds": ["<id>", "..."] }`; reorder every question in a topic.

Questions require a `topicId`, a `title` and an `answer`. Optional `content` accepts up to 20 `{ "kind": "text" | "code" | "json", "value": "..." }` parts. Optional `mediumUrl` and `compilerUrl` must be HTTP(S) links. Moving a question to another topic appends it to that topic's order.

All JSON errors use `{ "error": "..." }`; invalid request details are returned as a `details` array.
